# 人员管理接口文档（Admin Persons API）

> 适用版本：RecordHub Workflow1 v0.2.0 及以上。
> 本文描述运行期维护人员数据的全部管理接口。

## 1. 数据语义（先读这一节）

- 服务启动时读取飞书人员表、部门表**各一次**（手机号批量换取 OpenID），结果持久化在
  `data/state/cache/organization.json`（每条人员记录包含 `open_id`）。
- **运行期间程序不再自动读取人员表**：飞书长连接收到人员/部门表变更事件不会触发重读，
  运行时流程也不会回源。只有两个入口会重新读表：项目重启，或手动调用第 5 节的
  `POST /admin/cache/organization/refresh`。
- 本文 1–4 节接口**只修改本地持久缓存，不写回飞书人员表**。下次重启或手动刷新会以飞书表
  为准整体覆盖本地缓存。**想让修改永久保留，必须同步修改飞书人员表**（或接受重启后丢失）。
- 修改对"下一个开始的自然日流程"生效；**已经冻结的当日快照不受影响**（同日重试、续跑
  仍使用旧人员关系）。
- 每次写操作后程序自动重算：`team_leader_id`（必须且只能一名"团队负责人"）和
  `anomalies`（组织异常清单），并在响应中返回。`anomalies` 非空时，新一天的流程启动会被
  校验拦截（"组织关系异常"），需尽快修正。

## 2. 鉴权

所有接口需要管理员 Token（`.env` 中 `RECORDHUB_ADMIN_TOKEN`）：

```
Authorization: Bearer <RECORDHUB_ADMIN_TOKEN>
```

- 未配置 Token：`503 Endpoint token is not configured`
- Token 缺失或错误：`401 Invalid bearer token`

以下示例假设服务在 `http://localhost:8000`，Token 存在环境变量 `ADMIN_TOKEN` 中
（Windows PowerShell 用 `curl.exe` 时把 `$env:ADMIN_TOKEN` 替换对应写法即可）。

## 3. 接口列表

### 3.1 查询人员列表

```
GET /admin/organization/persons
```

响应 `200`：

```json
{
  "team_leader_id": "reczz28JHxNvmBli",
  "anomalies": [],
  "persons": [
    {
      "person_id": "reczz28JHRONoyan",
      "name": "王金丰",
      "role": "骨干学生",
      "department_id": "001",
      "leader_id": "reczz28JHSqwV93N",
      "open_id": "ou_f68fbaa465973654a4615c133ac04680",
      "source_record_id": "reczz28JHRONoyan",
      "active": true
    }
  ],
  "departments": [
    {"department_id": "001", "name": "宣传部", "minister_id": "reczz28JHSqwV93N",
     "source_record_id": "recxx", "active": true}
  ]
}
```

字段说明：

| 字段 | 类型 | 说明 |
|---|---|---|
| `person_id` | string | 人员编号，全流程唯一键（飞书表读取时=「人员编号」列，缺省用记录 ID） |
| `name` | string | 姓名 |
| `role` | string | 角色：`基层学生` / `骨干学生` / `部长` / `团队负责人` |
| `department_id` | string \| null | 所属部门编号 |
| `leader_id` | string \| null | 直属上级的 `person_id`（基层学生的上级须是骨干学生，骨干学生的上级须是部长） |
| `open_id` | string \| null | 飞书 OpenID，通知发送使用 |
| `source_record_id` | string \| null | 来源飞书记录 ID（仅读表刷新时产生） |
| `active` | bool | 是否有效；`false` 的人不参与评价与通知 |

### 3.2 新增人员

```
POST /admin/organization/persons
Content-Type: application/json
```

请求体（`person_id`、`name`、`role` 必填且不能为空，其余可选）：

```json
{
  "person_id": "P2026001",
  "name": "张三",
  "role": "基层学生",
  "department_id": "001",
  "leader_id": "reczz28JHRONoyan",
  "open_id": "ou_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
  "active": true
}
```

成功 `201`：返回与 3.1 相同结构的全量最新数据。

错误：

- `400`：必填字段为空或字段名不在允许列表（多余字段一律拒绝）
- `409`：`person_id` 已存在

### 3.3 修改人员

```
PUT /admin/organization/persons/{person_id}
Content-Type: application/json
```

请求体**只传要修改的字段**（`name`、`role`、`department_id`、`leader_id`、`open_id`、
`active` 的子集，至少一个）。`person_id` 本身不可修改。

```json
{"role": "骨干学生", "leader_id": "reczz28JHSqwV93N"}
```

清空语义：`department_id`、`leader_id`、`open_id` 传空字符串 `""` 表示置为空。

```json
{"open_id": ""}
```

成功 `200`：返回全量最新数据。

错误：

- `400`：未提供任何字段，或 `name`/`role` 传入空值
- `404`：`person_id` 不存在

### 3.4 删除人员

```
DELETE /admin/organization/persons/{person_id}
```

从本地缓存移除该人员。其他人员指向其的 `leader_id`、部门 `minister_id` 会变成悬空引用，
重算后会出现在 `anomalies` 中（例如"人员 S1 的直属上级不存在"）。若只是想临时停用，
建议改用 `PUT` 设置 `{"active": false}`。

成功 `200`：返回全量最新数据。错误 `404`：人员不存在。

### 3.5 手动回源刷新（读取飞书人员表/部门表）

```
POST /admin/cache/organization/refresh
```

**用飞书表内容整体覆盖本地缓存**，同时完成手机号→OpenID 换取。接口不接受请求体。

响应 `200`：

```json
{"persons": 12, "departments": 3, "anomalies": []}
```

`anomalies` 非空说明飞书表数据本身有组织关系问题，需先在飞书表修正。

## 4. 典型流程

```bash
# 新成员入职（当天生效，无需重启；要持久请之后同步改飞书表）
curl -s -X POST http://localhost:8000/admin/organization/persons \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"person_id":"P2026001","name":"张三","role":"基层学生","department_id":"001","leader_id":"B1","open_id":"ou_..."}'

# 成员换飞书账号（修正 open_id）
curl -s -X PUT http://localhost:8000/admin/organization/persons/P2026001 \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"open_id":"ou_新的ID"}'

# 成员退出
curl -s -X DELETE http://localhost:8000/admin/organization/persons/P2026001 \
  -H "Authorization: Bearer $ADMIN_TOKEN"

# 已在飞书表改好人员数据，想立即生效（不重启）：先改表，再刷新
curl -s -X POST http://localhost:8000/admin/cache/organization/refresh \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

## 5. 已知限制

- 修改不落飞书表：重启或 3.5 刷新会覆盖 1–4 节接口的全部改动，这是当前版本的明确设计。
- 新增人员没有 `source_record_id`，不影响流程；下次 3.5 刷新后以飞书表记录为准。
- 通过接口直接设置 `open_id` 时程序不校验其在飞书中是否真实存在；填错只会在发送通知时
  暴露，建议修改后用 `GET` 复核。
- 删除当日快照中已有评价任务的人员不会影响已生成的当日流程。
