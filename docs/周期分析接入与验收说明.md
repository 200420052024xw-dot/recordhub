# 周期分析接入与验收说明

S04—S09 现已接入材料准备、现有飞书表格读写、周期调度、通知、人工确认和状态恢复。AI 只生成经校验的 JSON 文字内容；部门权限、日期、统计、记录关联和运行状态由 Python 处理。

## 1. 运行范围与周期

| Skill | 执行人和范围 | 默认材料范围 |
| --- | --- | --- |
| S04 | 各部长分别处理所管理的部门，负责人独立处理全团队 | 最近三个完整自然日，每三天执行 |
| S05、S06、S07 | 各部长分别处理所管理的部门，负责人独立处理全团队 | 上一自然月，每月执行 |
| S08、S09 | 团队负责人 | 上一完整自然周，每周执行 |

沿用 `config/schedules.toml` 的北京时间和具体时刻。三天周期按 `anchor_date` 计算，重启不会重新起算。团队负责人直接使用原学生检查记录，不依赖部长的人员建议、idea 或谈话名单。部长管理多个部门时分别生成任务、分别选配置版本。

调度可配置 `department_ids` 和 `user_ids` 限定实际执行对象；权限仍按组织缓存中的有效人员、部长归属和团队负责人核对。每个任务保存最终使用的部门范围。

首次启用只补最近一个应执行周期，避免从起算日批量发送历史通知；之后通过持久化调度检查点补执行服务离线期间错过的周期。缺材料任务每十五分钟重试，重启也会恢复。已生成任务复用保存的输入、配置及模型结果。

## 2. 材料与历史保存

`data/state/workflow1/` 保存短期每日运行状态；新增 `data/state/checked/workflow1/` 长期保存已完成的原检查快照。每日完成时保存，清理旧运行状态时也会先保存快照。仓库当前的两天清理规则继续用于运行状态，长期检查材料另行保留。

程序逐日读取冻结的人员名单、有效日志和最终评价，以及 AI 建议和人工评价各自的来源。仓库当前每日读取采用同一人同日最后一条日志，先前快照中已经保留的多条日志仍全部纳入。旧快照没有评价时间时保留 `null`，不伪造时间；新增快照分别记录 AI 生成和确认时间。人工评价的时间是程序接受确认的时间。

单日、跨日统计分别记录去重人数与人次：`expected_people/submitted_people/missing_people` 和 `expected_person_days/submitted_person_days/missing_person_days`。跨日的 `missing_people` 是范围内始终未交的人员，某日未交但其他日期已交的情况计入未交人次。完整范围的统计保存在结果外层的 `material_statistics`，不是 AI 生成的内容。

日期缺失、提交核算冲突、未确认评价或评价身份不一致都会使任务进入 `BLOCKED`，不调用模型；此时统计为 `null`，不将未知情况算成未交。确认人收到一次等待材料通知，补齐后自动续跑。完整范围没有已交文字时写回 `NO_MATERIAL`，不编造分析条目。

以前已经被删除的快照不能由代码自动还原。启用月度分析前需确认上月检查材料完整；可以从原服务备份恢复相应的每日状态文件或已完成快照，再恢复等待任务。不要只用当前人员名单推测历史组织关系。

成果出处和课程、技术编号也支持可选的已有文本列映射：`logs.fields.achievement_refs` 存放出处 JSON 数组，`logs.fields.resources` 存放资源 JSON 数组（`resource_id/name/category/description`）。程序把它们带入每日快照，并为资源补入原记录来源。没有这些列时省略映射，S08 的出处和 S09 的可用资源编号保持为空；不会假定已经检索公共库，也不自动新增列。资源编号定义冲突时等待修正材料。

## 3. 飞书结果保存

继续使用现有表和字段，不自动创建业务表或新列。每个任务一条记录，`文本` 的第一行保存 `RecordHub:Sxx:<任务UUID>`，用于外部写入和重试核对。

| 范围 | 目标表 | 结果列 |
| --- | --- | --- |
| 部门 S04—S07 | `department_analysis` | 各 Skill 已有的分析列 |
| 团队 S08—S09 | `team_analysis` | `公共技术`、`公共培训建议` |
| 团队 S04—S07 | `team_analysis` | 优先采用配置中对应的独立列，其次 `result_json`；两者都未配置时，在已有 `文本` 列的业务标识后保存完整 JSON |

JSON 包含来源、范围、配置版本、程序统计、待确认或已确认状态和确认人。分析列、通用 JSON 列和 `文本` 列必须为可写文本字段；部门 `部长` 映射按人员字段、`日期` 按日期字段写入，生成模型结果前检查实际类型。

如果希望团队 S04—S07 也分列展示，只需将已经存在的相应文本列加入映射；本版不替你改变真实飞书表结构。示例配置末尾提供了可选映射。

创建成功但响应丢失时，恢复任务会先核对飞书原记录，再补本地映射，避免重复创建。待确认的内容若已人工修改，普通续跑会保留这些修改。

## 4. Skill 版本配置

内置默认模板无需编写提示词即可使用。可选择将 `config/skill_versions.example.json` 复制为 `config/skill_versions.json`，填入真实部门、使用人和版本号后启用。

程序也会读取已经配置的飞书 `prompts` 表。现有 `分析skill` 文本单元格中填写完整 `SkillConfig` JSON 对象或数组；无需新增版本列。个人配置里的 `user_id` 必须与该行 `使用人` 字段一致，部门默认配置的 `使用人` 留空。不能把没有 Skill 编号和归属的旧纯提示词自动猜成某个配置。

本地与飞书配置合并后按“个人版 → 部门默认版 → 内置默认模板”选择；同一级出现多个启用版本会报错。每个分析任务在模型调用前冻结所选配置。默认模板升级不静默改变旧修改版。

## 5. 启用与手动运行

确认部署环境具备现有依赖、飞书读写和消息权限；在实际 `config/tables.toml` 中填写 `department_analysis/team_analysis` 的真实表 ID 和已有字段映射。

新增环境配置：

```dotenv
RECORDHUB_ANALYSIS_ENABLED=true
RECORDHUB_SKILL_CONFIG=config/skill_versions.json
RECORDHUB_TEAM_SKILL_DEPARTMENT_ID=TEAM_MANAGEMENT
```

未设置分析开关时默认为关闭自动调度。填写配置、启用并重启服务后开始自动执行；管理接口和手动命令可以单独运行。`TEAM_MANAGEMENT` 只是配置归属编号，可以替换为实际管理部门编号，不会扩展数据权限。

运行某部门一次分析（人员编号、部门编号和日期换成实际值）：

```powershell
python main.py run-analysis --skill S04 --start 2026-10-01 --end 2026-10-03 --user-id minister-person-id --department-id department-id
```

负责人全团队分析省略 `--department-id`。同一参数再次运行会复用任务；需要新一版人工重跑时传入 `--revision 2`，旧任务保留。

```powershell
python main.py resume-analysis --run-id task-uuid
python main.py confirm-analysis --run-id task-uuid --user-id minister-person-id
python main.py confirm-analysis --run-id task-uuid --user-id minister-person-id --content-file edited_content.json
```

修改文件只包含对应 Skill 的 `content` 对象。确认前会读取飞书记录、检查来源元数据，并校验人工修改后的字段、人员和来源。确认后保留初始 AI 草稿和已确认结果，任务进入 `CONFIRMED`；人员和资源安排仍由人决定。

## 6. 管理接口

所有接口要求 `Authorization: Bearer <RECORDHUB_ADMIN_TOKEN>`。这是受信任管理端的接口，`user_id` 表示管理端代哪位确认人执行，不能把它当作飞书成员自身的登录认证。

| 方法与路径 | 用途 |
| --- | --- |
| `POST /admin/analyses` | 传入 Skill、范围、使用人及可选部门、修订号，创建或恢复任务 |
| `GET /admin/analyses/{run_id}` | 查看材料范围、统计、状态、草稿和结果 |
| `POST /admin/analyses/{run_id}/resume` | 重试或补齐材料后续跑 |
| `POST /admin/analyses/{run_id}/confirm` | 本任务指定确认人确认，可携带修改后的 `content` |
| `POST /admin/analyses/{run_id}/notifications/reconcile` | 管理员核对发送结果后登记 `message_id`，可指定 `blocked=true` 表示等待材料通知 |

确认人先在飞书表核对文字，再由受信任管理端或本地命令执行确认。本版提供后台接口和命令，不新增 Web 页面，也不会把人工编辑飞书单元格直接当成已经确认。

通知采用稳定 UUID。发送结果未知且超过飞书去重窗口时停下发送，需管理员先核对真实消息，再登记消息 ID 并恢复任务。

## 7. 本轮验证与待验收项

自动测试覆盖自然月和自然周、三天起算日、长时间离线补跑、材料缺失、评价确认依赖、跨日统计、历史保存、部门权限、真实字段选择、写入响应丢失、人工修改、确认写回失败、通知去重及管理接口认证。

本轮使用模拟飞书与模型响应进行验证。新增周期能力仍需在你的真实租户验收：实际分析列类型、配置表内容、通知接收人及确认后的写回。现有每日流程的运行事实以你提供的已跑通状态为准。

此前开发版本曾通过全量 75 项测试；当前目录缺少当时新增的三个测试文件，该数字不是本次合并后的测试结果。本次结果见合并说明。
