# Workflow1 改造目标文档

> 本文定义 RecordHub 每日工作日志流程的改造目标，供后续设计、开发和验收使用。它描述的是目标行为，不代表当前代码已经实现。若旧文档中的 Workflow1 流程或文档形式与本文冲突，以本文记录的本次需求为准。

本次实施补充约束：Workflow1 只使用一个逐日志 Prompt（`prompts/S01.txt`）；组织关系、评价归属、截止收口、部门和团队文档均由代码完成。飞书多维表格以 `学生工作日志层级管理系统 .xlsx` 的现有列为准，人员表填写手机号，由程序查询飞书 OpenID，无需成员填写 OpenID。AI 与人工评价分别写入现有 `AI评价表`、`人工评价表`；人工表的自动评价编号独立生成，程序按被评价人、直属评价填写人和时间匹配唯一日志。日期、业务键、通知和文档 Token 保存在本地状态。

## 1. 目标与边界

系统以飞书多维表格中的人员、部门和工作日志为输入，以 DeepSeek 处理日志，以飞书问卷收集骨干和部长的评价，以飞书云文档呈现每日结果。系统按“成员 → 骨干 → 部门 → 团队”的组织关系推进，并能在人工未完成或长连接消息缺失时按设定时间继续。

系统不负责代替成员填写原始工作日志。原始日志仍以飞书多维表格中的记录为来源。对同一天的任务，程序保存不可随意改变的人员与日志快照，所有重试和恢复使用同一快照。

## 2. 每日 Pipeline

```text
项目重启/手动刷新 → 读取人员表一次（换取OpenID） → 更新常态组织缓存
人员变更 → 管理接口（增删改查） → 更新常态组织缓存
                                   ↓
每日定时启动 → 读取昨天全部日志一次 → 保存当日快照
                                   ↓
按日志逐条调用 LLM（有并发上限）→ 等全部处理结束
                                   ↓
批量写回 AI 评价 → 骨干／部长各收到一次问卷通知
                                   ↓
监听问卷结果，逐个核对评价完成情况
             ├─ 已完成：采用人工填写结果
             └─ 截止仍未完成：采用已生成的 AI 结果继续
                                   ↓
形成各骨干同学小组日志 → 形成各部门日志文档
                                   ↓
全部部门就绪 → 形成 MM-DD 团队日志 → 通知团队负责人
```

### 2.1 常态组织缓存

- 系统持续保存人员、部门及上下级关系，包括稳定人员编号、姓名、角色、所属部门、直属上级、部门部长、团队负责人、飞书 OpenID 和有效状态。
- 人员表和部门表只在项目重启时各读取一次（手机号换取 OpenID 后连同 OpenID 一起持久化），运行期间程序不再自动重读；飞书长连接事件不触发组织缓存重读。运行期的人员调整通过管理接口对持久缓存做增删改查（接口只改本地缓存、不写回飞书表，重启会重新以飞书表为准；需要立即采用飞书表改动时可手动触发回源刷新）。启动回源失败但本地已有持久缓存时，使用持久缓存继续运行。
- 某日流程开始时冻结一份当日组织快照。处理中发生的人员变更进入常态缓存，供后续日期使用，不悄悄改变已启动任务的评价归属。
- 缺少关键身份或上下级关系时记录异常，不能把无法匹配的日志任意分配给其他评价人。管理接口的每次写操作都会重算异常清单并在响应中返回。

### 2.2 一次性读取昨天日志

- 以 `Asia/Shanghai` 计算目标日期。每天在配置时间读取前一自然日的全部日志，完成分页后一次性保存到当日快照。
- 快照保存符合日期条件的原始日志、记录 ID、提交人、提交时间，以及应交／已交／未交状态。**每人每天只保留最后提交的一条日志**，更早的提交被取代并记入异常台账（顺带保证问卷按被评价人＋填写人总能唯一定位日志）。
- 单点数据异常不拖垮整天：提交人不在人员表的日志跳过并记台账；缺提交时间的日志按邻近记录（表格即填写顺序）的时间回填；未交的人在 AI 评价表回写一行「未填写日志」标注。所有跳过/失败记入当日异常台账并即时通知管理员（`RECORDHUB_ADMIN_OPEN_ID`），详见 [异常流程与重评接口](异常流程与重评接口.md)。
- 后续 LLM、评价、文档生成均以当日快照为输入，不在每个阶段重复扫描昨天的日志表。服务重启后继续使用已保存快照。

### 2.3 逐日志 LLM 处理与批量写回

- 每条已提交日志是一个独立 LLM 处理单位；未交日志只形成未交状态，不编造日志或评价。
- LLM 请求异步执行，设置可配置的同时运行上限。每条结果都要校验与原日志、人员和目标日期的对应关系。单条重试耗尽后标注「AI 生成失败」跳过并记台账、通知管理员，**全天继续**；自动路径（定时、启动恢复、截止放行）不再重评失败项，只有重评接口（`POST /admin/workflows/{日期}/resume`，只重跑失败与未处理项）可手动重评。
- 等当天所有需要处理的日志都有有效结果后，再按批次写入 AI评价表。人工结果由现有人工评价表承接。程序在本地以日期、日志、评价人建立稳定业务键，并在重试前核对飞书的原日志关联、提交人和评价人，避免重复评价。
- 骨干负责直属成员日志，部长负责直属骨干日志。程序负责确定评价范围，LLM 不自行推断上下级关系。

### 2.4 一次通知、问卷填写与确认

- AI 评价写回成功后，每位需要评价的骨干／部长按目标日期收到一次飞书消息。消息包含评价范围以及固定问卷链接：

  <https://jwxnd3ayslt.feishu.cn/share/base/form/shrcn4Atuvh0rgPngi5TMQCoxmg>

- 问卷结果必须能关联目标日期、填写人、被评价人和原日志。系统为每位骨干／部长记录应评价、已评价、未评价的项目，并只在其责任范围内判断是否完成。
- 系统通过飞书长连接监听问卷结果落入的多维表格记录变化，后台重新读取记录并推进对应范围；重复事件不得重复确认、通知或生成文档。
- 通知去重以飞书发送成功为依据。发送失败可重试；已发送成功不得重复发送。
- 到设定截止时间，已提交的人工意见保持有效，未提交项按已有 AI 内容放行并在文档标注「人工未评价」（快照记 `manual_skipped`）。AI 生成失败的条目不阻塞截止放行，文档标注「评价生成失败」。云文档被人工编辑过时以人工版本为准，程序停止续写该文档并记台账。没有收到长连接事件时，也要主动核对飞书记录；服务错过截止时间后恢复，应补做截止推进。
- 截止放行后，新就绪的骨干、部门和团队阶段应继续推进，不应每一级都额外等待下一天的截止任务。

## 3. 云文档结构与内容归属

本节的 `【文档名】` 表示**可点击并跳转到另一篇飞书云文档的引用**。**统计上浮**：团队统计写在团队文档，部门统计写在团队文档的部门小节，小组统计（唯一点名未交人的地方）写在部门文档的小节；小组文档只放逐人日志。不同部门、小组、人之间用分隔线隔开，单人日志的各部分之间不空行。

```text
MM-DD 团队日志
├─ 提交情况（应交／已交／未交人数，整数）
├─ xx老师部门：＋部门提交情况（整数）＋【MM-DD 部门名日志】
│   └─ 打开后按骨干排小节：
│       xx同学 ＋ 该小组提交情况（未交者点名） ＋【MM-DD xx同学小组日志】
│           └─ 打开后逐人日志块：
│               xx骨干本人的日志 → 分隔线 → 每位成员的日志
│               -所属部门／-角色／-是否为骨干／-时间
│               #### 日志内容 → #### 评价（-评价人/-评价时间/-肯定之处/-改进之处）
```

### 3.1 团队日志

- 每个目标日期生成一篇 `MM-DD 团队日志`，开头为团队整体提交情况（仅整数）。
- 随后按部门排列 `xx老师部门：` 小节：部门整体提交情况（仅整数）＋ `【MM-DD 部门名日志】` 引用。不复制各部门、骨干和成员的全文。
- 各部门的文档就绪后，团队日志才标记为完整，并发送给团队负责人（称呼口径：部长／团队负责人＝老师，骨干＝同学，与通知一致）。

### 3.2 部门日志

- 每个部门、每个目标日期生成一篇 `MM-DD 部门名日志`。文档按骨干排列，小节标题为 `xx同学`。
- 每个小节写该小组提交情况（应交／已交／未交人数），**未交者在本节点名**（全系统唯一允许点名的位置），然后放置 `【MM-DD xx同学小组日志】` 引用。
- 部门文档不放部门自身的汇总统计（在团队文档），也不复制成员逐人日志全文。一个部门所需的骨干材料就绪后即可生成该部门文档，不等待其他部门。完成后把文档发给对应部长。

### 3.3 骨干的小组日志

- 每位骨干、每个目标日期有一篇 `MM-DD xx同学小组日志`。**骨干本人的日志块排最前，随后是每位直属成员**，人与人之间用分隔线隔开。
- 每人一个日志块，行序为：`-所属部门：<编号·名称>`、`-角色：<基层学生／骨干学生／部长／团队负责人>`、`-是否为骨干：<是／否／不适用>`、`-时间：<提交日期>`、`#### 日志内容`、`#### 评价`；块内各部分之间不空行。
- 已交者呈现日志内容与最终评价；评价人写 `姓名，角色`，截止放行用 AI 时写 `系统AI（人工未评价）`，LLM 失败写 `评价生成失败（可重评）`；未交者也输出完整块，日志内容为 `未填写日志`、评价为 `未评价`。
- 小组统计不放在小组文档（在部门文档的小节）。

### 3.4 文件夹与链接

- 按日志所属日期建立每日飞书文件夹，文件夹名采用完整日期 `YYYY-MM-DD`。其中保存 `MM-DD 团队日志` 和按部长命名的文件夹；部长文件夹下保存对应部门文档及其骨干的成员日志文档。骨干文档也可置于各骨干子文件夹中，以保持之前约定的分层归档方式。
- 文件夹、文档和引用都以目标日期及稳定部门／人员编号建立幂等映射。重启、重试或补跑时复用已有对象，不能重复创建同名文档。
- 多维表格中的报告记录保存文档 URL；本地流程状态保存文档 Token、业务键及状态，便于查找和恢复。上级文档保存下级文档引用，不复制下级正文。

## 4. 状态、失败与完成条件

- 工作流记录每日快照、每条日志的 LLM 状态、批量写回状态、各评价人的问卷完成状态、通知发送状态、各级文档 Token 与 URL、部门及团队推进状态。
- 已完成日期的状态保留 2 天（昨天评价的＋今天评价的），作为后续流程（如 workbuddy）的近期数据入口；未完成状态不因保留期被清理。
- 外部写入采用幂等键。发生部分成功时先核对飞书已有记录或文档，再补齐缺失项；不能因重试造成重复消息、评价或文档。
- 长连接只负责尽快推进。即使事件断开或漏投，截止任务及恢复逻辑也能重新读取外部状态并继续。
- 某日只有在评价已按人工结果或截止规则收口、所有骨干成员日志文档及部门文档就绪、团队日志引用完整、通知完成且外部对象映射保存后，才能标记完成。
- 人员关系、Prompt 配置、飞书字段或文档权限不满足要求时，记录可定位的失败原因，保留快照供修复后续跑。

## 5. 验收场景

1. 人员变更通过管理接口（或重启回源）进入常态缓存；已经开始的日期仍使用冻结的组织快照。
2. 同一人昨天提交两条日志，快照只保留最后一条并完成 LLM 处理，更早一条记入异常台账；处理完成后才发生当天评价批量写回，未交者在 AI 评价表有「未填写日志」标注行。
3. 多个骨干的日志处理并发运行，但同时请求数不超过配置上限。单条失败后重试不会产生重复评价。
4. 每位骨干／部长只收到一条包含指定问卷链接的通知；问卷填写进度能精确对应其负责的日志。
5. 人工已填写部分与截止自动采用 AI 的部分可以共存；长连接消息丢失或服务错过截止时，流程仍能补偿推进。
6. A 部门完成后先生成 A 部门文档并通知 A 部长；B 部门尚未完成不阻塞 A 部门。团队日志等待全部有效部门就绪。
7. 打开团队日志可见团队提交情况与 `xx老师部门：` 小节并点击部门引用；打开部门文档可见 `xx同学` 小节的小组提交情况（点名未交人）并点击小组日志引用；小组文档中骨干本人排最前、成员逐人成块且人与人之间有分隔线。
8. 同一天的流程重启、重试、补跑后，评价记录、飞书文件夹、云文档和通知均不重复。

## 6. 尚需确认的细节

以下细节未由本次对话确定，实施前需确认，不能据此擅自改变上面的内容层级：

- 部门文档中“骨干本人日志情况”的展示格式：保留日志原文、LLM 整理内容，或二者并列。
- 真实飞书租户已核对：人工评价表的 `评价编号` 与 AI 评价编号独立生成；问卷靠被评价人和直属评价填写人匹配。同一人同日多条日志的歧义已按「每人每日只保留最后一条」的策略消除，不再要求问卷增加原日志标识。
- 飞书归档的固定父文件夹位置，以及骨干子文件夹是否必须创建。
- 若某骨干没有直属成员、某部门当日无人提交日志，文档是否仍创建以及空内容展示文案。

## 7. 与当前代码的差距

本次代码改造已经实现每日组织与日志快照、逐日志单 Prompt、AI 与人工评价分表核对、截止补偿、人员管理接口（本地持久缓存的增删改查＋手动回源刷新）、三级文档引用和本地幂等映射。仍需在真实飞书租户核对问卷关联、文档权限与字段类型，并配置归档父文件夹 Token 后端到端验收。
