# 服务器部署

生产环境：腾讯云 VM，代码在 `/root/recordhub`，由 systemd 托管。**只允许一个进程** —— 日志轮转和 `data/state/` 都不支持多进程共写。

## 唯一正确的启动方式

```bash
systemctl restart recordhub.service
```

**不要手工运行 `.venv/bin/python main.py serve`。** 2026-10-15 的事故就是这么来的：有人在 SSH 会话里手工起了一个 `serve`，忘了关，它占住 8000 端口；systemd 从此再也起不来，又因为没有重启上限，空转了 10 小时 1984 次，顺带发出约 2000 条管理员告警。

一定要手工验证的话，用别的端口，并且用完就关：

```bash
.venv/bin/python main.py serve --host 127.0.0.1 --port 8001
```

## systemd unit

`/etc/systemd/system/recordhub.service`：

```ini
[Unit]
Description=RecordHub daily log analysis
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
WorkingDirectory=/root/recordhub
ExecStart=/root/recordhub/.venv/bin/python /root/recordhub/main.py serve --host 0.0.0.0 --port 8000
ExecStartPre=/root/recordhub/scripts/recordhub-port-check.sh 8000
Environment=PYTHONUNBUFFERED=1
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

改完记得 `systemctl daemon-reload`。

## 必需的退避配置

`/etc/systemd/system/recordhub.service.d/backoff.conf`：

```ini
[Unit]
StartLimitIntervalSec=300
StartLimitBurst=5

[Service]
RestartSec=10
```

没有 `StartLimit` 时，`Restart=always` + 短间隔等于一台永动机：systemd 默认的
`StartLimitBurst=5 / StartLimitIntervalSec=10s` 在 5 秒间隔下永远凑不满，所以它永不放弃。
加上这两行之后，失败 5 次服务会**停下来并标成 `failed`** —— 这是一个能被人看见的状态。

`RestartSec=10` 让崩溃循环慢下来，给日志和告警留出可读的间隔。

## 端口预检

`scripts/recordhub-port-check.sh` 由 `ExecStartPre` 调用，端口被占时立即失败并打印占用进程，
而不是等 uvicorn 跑完整个启动流程再抛 `[Errno 98]`。脚本随代码一起部署：

```bash
chmod +x /root/recordhub/scripts/recordhub-port-check.sh
```

## 部署步骤

```bash
cd /root/recordhub
git status --short                                   # 有本地改动先处理，否则 pull 会冲突
git pull origin main
.venv/bin/python -m unittest discover -s tests       # 自检
systemctl restart recordhub.service
```

确认起来了：

```bash
systemctl is-active recordhub.service
ss -lptn 'sport = :8000'
tail -n 20 logs/recordhub.log
```

看到 `Uvicorn running on http://0.0.0.0:8000` 且后面**没有** `[Errno 98]` 就算成功。

## 排查端口占用

```bash
ss -lptn 'sport = :8000'
ps -fp <PID>
readlink -f /proc/<PID>/cwd      # 从哪个目录跑的
systemctl status <PID>           # cgroup 落在 session-*.scope 还是 /system.slice/
```

cgroup 是 `session-*.scope` 说明是有人手工起的（会话断开后进程被 init 收养）；
落在 `/system.slice/` 才是 systemd 正常拉起的。

## 告警抑制

同一类错误在 `AdminAlertHandler.SUPPRESS_MINUTES`（默认 360 分钟）内只发一条，去重记录
存在 `data/state/admin_alerts.json`。**这个记忆必须落盘** —— 进程内去重挡不住崩溃重启循环，
每次重启都是新的空记忆。把 `SUPPRESS_MINUTES` 设为 0 即关闭跨进程抑制。
