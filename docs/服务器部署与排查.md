# 服务器部署与排查

本文面向 Linux 服务器(腾讯云 OpenCloudOS)。README 里的部署命令是 Windows 写法(`.\.venv\Scripts\python.exe`),服务器上不适用,以本文为准。

## 1. 服务是怎么起的

由 systemd 托管,单元名 `recordhub`。

```bash
systemctl cat recordhub
```

关键几行:

```ini
WorkingDirectory=/root/recordhub
ExecStart=/root/recordhub/.venv/bin/python /root/recordhub/main.py serve --host 0.0.0.0 --port 8000
```

- **python 路径必须是 `/root/recordhub/.venv/bin/python`**,这个 venv 里装着依赖,换别的解释器会 `ModuleNotFoundError`。
- `--host` 必须是 `0.0.0.0`。写成 `127.0.0.1` 时只有服务器本机能访问,外部一律连不上。

> `systemctl cat` 的长行会被 less 截断(行尾显示 `>`),要看完整内容用 `cat /etc/systemd/system/recordhub.service`。

## 2. 常用命令

```bash
systemctl status recordhub          # 当前状态
systemctl restart recordhub         # 重启(改完配置、更新代码后用)
journalctl -u recordhub -n 50       # 最近 50 行日志
tail -f /root/recordhub/logs/recordhub.log   # 跟踪应用日志
```

## 3. 让外部能访问

两处都要对:服务器监听地址、云安全组。

**① 改成监听 0.0.0.0**

```bash
cp /etc/systemd/system/recordhub.service /root/recordhub.service.bak
sed -i 's/--host 127\.0\.0\.1/--host 0.0.0.0/' /etc/systemd/system/recordhub.service
grep ExecStart /etc/systemd/system/recordhub.service     # 确认已改成 0.0.0.0
systemctl daemon-reload
systemctl restart recordhub
ss -lntp | grep 8000                                     # 要看到 0.0.0.0:8000
```

也可以用 drop-in(`systemctl edit recordhub`)覆盖,但注意两点:drop-in 里第一行必须写空的 `ExecStart=` 清掉原命令;存盘按键取决于编辑器,vi 是 `:wq`,`nano` 是 `Ctrl+O` 回车再 `Ctrl+X`。

**② 云安全组**

入站规则放行 TCP 8000,来源 `0.0.0.0/0`。

**③ 从外部验证**(不要用服务器自己 curl,那会绕过网络)

```bash
curl -m 5 http://<服务器公网IP>:8000/health/ready
```

## 4. 更新代码

```bash
cd /root/recordhub
git pull --ff-only origin main
systemctl restart recordhub
```

`--ff-only`:能快进就快进,服务器上有本地提交时直接报错停下,不自动合并。

拉不下来又看不出原因时,先看这两个:

```bash
git log --oneline -1                  # 是否已是最新提交
git status --short                     # 有没有本地改动挡住 pull
```

`config/schedules.toml` 若在服务器上被手工改过,pull 会拒绝,先处理本地改动。

## 5. 配置检查

```bash
cd /root/recordhub
.venv/bin/python main.py check-config
```

输出里要能看到 `workbuddy_entry` 这一段:

```json
"workbuddy_entry": {
  "submit_window": "12:00-23:50",
  "fallback_form_configured": true,
  "token_configured": true
}
```

- `submit_window` 读的是 `config/schedules.toml` 中 `[workflows.daily_log_reminder]` 的 `submit_opens_at` / `submit_closes_at`,**这两行缺失会让服务启动直接失败**,必须随代码一起更新。
- `token_configured` 为 `false` 时,接口会返回 503。

## 6. 环境变量

`.env` 不进版本库,新部署或换机器要手工补齐。对话入口需要:

```
RECORDHUB_WORKBUDDY_TOKEN=<给 WorkBuddy 用的那把串>
```

它和 `RECORDHUB_ADMIN_TOKEN` 是两把不同的钥匙:前者只能提交日志,拿它访问 `/admin/*` 返回 401。

## 7. 验证对话入口

```bash
# 不带 token → 401
curl -s -o /dev/null -w '%{http_code}\n' -X POST \
  http://<服务器公网IP>:8000/workbuddy/v1/work-logs/identity

# 带 token → 200,并返回人员信息
curl -s -X POST http://<服务器公网IP>:8000/workbuddy/v1/work-logs/identity \
  -H "Authorization: Bearer <RECORDHUB_WORKBUDDY_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"name":"张三"}'
```

手工触发一次日志写回(把缓存里的提交写进飞书日志表):

```bash
.venv/bin/python main.py flush-workbuddy --date 2026-10-10
```

## 8. 排查对照表

| 现象 | 原因 |
|---|---|
| 从外部**超时** | 服务没监听 `0.0.0.0`,或安全组没放行 |
| 从外部**连接被拒** | 端口没在听,服务没起来 |
| 502 | 前面那层代理连不上后端;直连 IP 时通常是服务未监听对外地址 |
| `/workbuddy/...` 返回 **404** | 服务在跑,但代码是旧的,重启一次 |
| 503 `Endpoint token is not configured` | `.env` 里没配 `RECORDHUB_WORKBUDDY_TOKEN` |
| 401 `Invalid bearer token` | 请求头写错,或 Bearer 与 token 之间多了空格/引号 |
| 启动即失败、所有路径都连不上 | 多半是 `check-config` 会报的配置问题(如 `schedules.toml` 缺 `submit_opens_at`) |

服务器本机自测(绕过网络,只看服务本身):

```bash
curl -s 127.0.0.1:8000/health/ready
ss -lntp | grep 8000
```
