# 消息发送与错误告警

## 自动发送规则

首次运行本版本时，在 `RECORDHUB_STATE_DIR/notification_delivery.json` 保存启用时间。启用前已有任务的未成功通知停止自动发送；启用后新任务正常发送当期通知。消息发送失败、结果未知或错过发送日期后，不自动补发。服务重启、人工评价事件、工作流恢复和自动收尾都受同一规则约束。

Workflow1 的部门汇总报告在人工评价当天北京时间 `22:00` 发送，由 `config/schedules.toml` 中的 `report_notify_at` 独立控制。凌晨任务只处理和生成日志，不发送部门汇总报告；如果报告在 22:00 后才生成，则生成完成后发送。

启动时只把已有且已准备好的待发消息保存到发送台账，不实际发送。台账独立于日报快照保留，因此快照清理后，仍可发送已经保存在台账中的消息。不要删除该台账，否则会丢失发送凭据和启用边界。业务流程仍可继续生成评价、文档和报告，发送失败不会阻断其他收件人。

消息台账记录日期、工作流、收件人、原消息文本、发送次数、结果、错误和 `message_id`。自动路径每条消息最多尝试一次；发送前先保存尝试状态，进程中断也不会导致自动重发。已成功的消息始终跳过，包括管理员调用接口时。

## 管理员按日期发送

`POST /admin/notifications/send`

沿用 `RECORDHUB_ADMIN_TOKEN`，通过 `Authorization: Bearer <token>` 鉴权。调用只发送已有的未成功通知，不重新执行 AI、不重新生成文档。

```json
{
  "dates": ["2026-10-06", "2026-10-08"],
  "workflow": "workflow1",
  "message_type": "report"
}
```

| 参数 | 可选值与含义 |
| --- | --- |
| `dates` | 必填，1—31 个日期；重复日期自动合并 |
| `workflow` | `all`（默认）、`workflow1`、`workflow2` |
| `message_type` | `all`（默认）、`review`（审核表单）、`report`（报告链接） |
| `kind` | 周期流程筛选：`all`（默认）、`stage`、`monthly`、`weekly` |
| `confirm_unsent` | 默认 `false`。仅在发送结果未知超过一小时、且管理员已核实没有送达时设为 `true`，允许重试未知项；已成功项仍跳过 |

日报日期是日志所属日期，例如 10 月 8 日日志一般在 10 月 9 日处理。周期流程日期是任务的计划运行日期，不是材料开始日期。选择 `all` 时，同一个日期分别按这两个含义匹配。

手动发送审核表单通知不会延长原有人工评价截止时间，也不会重新打开已经关闭的评价流程。补发历史报告时选择 `message_type: "report"` 即可。

PowerShell 调用示例：

```powershell
$headers = @{ Authorization = "Bearer $env:RECORDHUB_ADMIN_TOKEN" }
$body = @{
    dates = @('2026-10-06', '2026-10-08')
    workflow = 'workflow1'
    message_type = 'report'
} | ConvertTo-Json
Invoke-RestMethod -Method Post `
    -Uri 'http://127.0.0.1:8000/admin/notifications/send' `
    -Headers $headers -ContentType 'application/json' -Body $body
```

响应按日期、工作流及每条消息列出结果：

- `sent`：发送成功，包含飞书 `message_id`。
- `already_sent`：此前已成功，本次跳过。
- `failed`：发送失败、收件人缺失或结果未知需核对，包含错误原因；其他收件人继续处理。
- `not_ready`：评价或文档尚未准备好，不生成内容、不发送空消息。
- `not_found`：快照／周期任务以及可恢复的台账消息均不存在。
- `unavailable`：对应工作流未启用。

HTTP 200 表示批量请求处理完毕，需查看每项结果，不能把 HTTP 200 当成所有消息均已送达。未提供或错误的管理员 Token 返回 401；日期／筛选参数非法返回 422；未配置管理员 Token 返回 503。

`GET /admin/notifications/2026-10-08` 使用相同鉴权，查看该日期的持久化发送台账。`suppressed` 表示已停止自动补发，`failed` 表示飞书明确拒绝，`attempting` 表示结果尚不确定，`sent` 表示已取得成功凭据。台账含原消息内容，仅供管理员访问。

## 日志和管理员告警

日志仍位于 `logs/recordhub.log`，每天轮转，保留时间由 `RECORDHUB_LOG_RETENTION_DAYS` 控制。程序保留英文事件码，方便搜索和程序分析，并在下一行增加 `中文说明=`。错误记录包含异常类型、完整堆栈、业务日期、工作流、处理阶段，并用 `业务上下文=` 和 `错误类型说明=` 给出中文含义；飞书请求额外包含方法、接口路径、HTTP 状态、错误码、请求 ID、响应详情和耗时。消息日志包含稳定业务键、收件人、发送尝试和成功凭据。访问 Token、API Key、长连接 ticket 等凭据会脱敏。

`RECORDHUB_ADMIN_OPEN_ID` 必须设置为实际管理员的飞书 OpenID。服务和命令行执行期间，错误日志和带异常堆栈的警告会立即进入独立的告警发送线程；AI 首次失败即可告警，不等待重试耗尽。同一个异常在不同层重复记录时只发一次告警。每次告警包含事件编号，日志记录告警排队与送达结果。

告警通道独立于业务停发规则及模拟收件人覆盖，直接发送给配置的管理员。飞书断网、权限不足或管理员不可达时无法保证告警送达，会记录 `admin_alert_delivery_failed`，并防止递归告警；不会把告警加入历史业务补发队列。未配置管理员 OpenID 时会明确记录 `admin_alerts_disabled`。

更新代码并重启服务后生效；接口本身不改变日程。缺少快照的历史任务在收尾时会记录 `not_ready` 并保留原失败原因；收尾中途失败时保留已完成的确认数量及失败阶段。
